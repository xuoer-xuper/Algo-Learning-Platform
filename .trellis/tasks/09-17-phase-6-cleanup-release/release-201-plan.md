## Evidence And Risks

1. `master` 与 `dev` 从共同祖先 `97fab601` 分叉。`git merge-tree --write-tree origin/dev origin/master`
   的只读预检列出22个冲突路径，包括TabManager、会话恢复、凭据捕获、TabStrip及测试。
   部分稳定版修复已通过后续squash进入dev源码；不能把缺少祖先关系误报为修复丢失。
   必须逐项合并并在最终树验证两条线行为，不能整体取一侧或绕过PR门。
2. 候选包含 migration 030：25张表的82个时间列转为INTEGER毫秒。安全入口迁移前使用SQLite
   backup API，失败恢复并写marker；成功升级后不能只重装2.0.0来降级，需要恢复030前备份。
   完整用户数据备份/恢复还包含配置、笔记图片等，不能把自动SQLite备份称为全profile备份。
3. 原Git规范曾将不可直接回退的数据格式升级列为major。现已改为按声明的对外兼容契约判断，
   内部迁移不自动触发major；2.0.1仍是候选，安全加固与真实交付兼容性审查不因版本号而省略。
4. rc.1固定fixture的35个迁移/辅助源码哈希与导出的v2.0.0源码一致，既有schema29→30测试
   可复用其结构依据；不伪称已验证精确release-era私人数据或安装升级/卸载。
5. 发布工具存在已知阻塞：`before:init`在版本写入前打包；自动发布提交与merge-commit tag约定
   冲突；当前检查的构建缺少`latest.yml`。旧发布说明仍混用npm与package-lock，需同步修正。

## Proposed Implementation Boundary

- 先在隔离检出中准备发布，不切换或清理原Drizzle工作区；保留所有已有改动和用户`.zcode/`。
- 保留“tag指向master的no-ff发布合并提交”约定。版本/CHANGELOG在发布准备PR中完成；
  master阶段只验证、打tag和发布，不再次提升版本或新增发布提交。
- 使用独立发布配置：禁止npm发布和Git发布提交，禁止conventional-changelog在合并后重写
  文件；保留npm插件作为package.json版本来源，`--no-increment`不等于禁用npm插件。
- builder显式配置GitHub更新元数据来源，构建使用`--publish never`，不让打包提前上传。
  发布前验证安装包、blockmap和latest.yml的存在、版本、文件名及哈希对应关系。
- 发布预检要求干净检出、指定版本2.0.1、HEAD与已验收master一致、合法合并落点、目标tag
  不存在且GitHub Release未发布；缺失或不一致时失败，不覆写已有发行物。
- 预期涉及release-it配置、最小发布校验脚本及其测试、builder配置、CHANGELOG/发布说明、
  Git规范中工具流程说明。合并冲突另逐文件审核，保持master修复与dev新契约，不附带重构。

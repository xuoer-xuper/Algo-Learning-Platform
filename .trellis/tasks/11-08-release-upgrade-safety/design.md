# 发布加固技术设计

## 1. 边界与证据

基线为dev `3702f01`，已发布基线为 `v2.0.0` / master `d2d2b0c`。只修现有生命周期与
发布工具的缺口，不引入PR #8的Drizzle代码、不重写001–030、不搬迁整个数据库域。
依据见 `research/upgrade-recovery-gaps.md` 及两份 `release-201-*.md`。

最小行为差距不是“没有任意降级”，而是备份未独立验证、异常终止无持久阻断、恢复文件
替换顺序不保留完整失败状态、配置归一化先于数据库保护，以及发行工具与安装验收缺口。

## 3. 入口与模块

生命周期仍由 `electron/db/connection.ts` 拥有，`electron/backup/sqliteMigrationBackup.ts`
保持已有适配入口，runner仍执行事务。确需新纯逻辑放模板位置：

- `src/main/db/legacy-ledger-validation.ts`：默认生产路径的连续台账校验，不引入Drizzle。
- `src/main/services/backup/lib/migration-checkpoint.ts`：本地记录解析、状态与路径校验。
- 配置原字节备份优先扩展已有边界；确需小模块时使用同一backup/lib目录。

保留 `initDbAtPathWithMigrationSafety(dbPath, options): Promise<Database>`。同步测试入口
及显式 `options.migrations`（含[]）仍支持合成迁移9001等，但不能绕过未解决的中断/恢复
失败记录，不供生产参数选择。既有backup/restore函数尽量保持签名，不新增通用存储框架。

## 4. 迁移恢复点协议

建议记录字段：`formatVersion: 1`、`attemptId`、本地数据库身份、备份basename、源/目标
台账、`state`、毫秒时间、备份SHA256，以Zod校验。不得含行数据、配置正文或Cookie；路径
必须限制在预期目录并核对数据库身份。错误分类与字段在实现前测试中锁定。

1. 检查未解决记录，再打开DB；全部post-open操作（包括pragma和台账读取）纳入close-on-error。
2. 默认路径验证已知连续version/name前缀；未来、缺口、错名、无台账但有业务表均拒绝，
   不迁移、不清孤立访问、不轮换备份、不清记录。不将打开WAL连接宣称为绝对零文件变化。
3. SQLite backup写独立partial文件，只读重开验证integrity及源台账，再提升为正式恢复点。
   partial或验证失败文件不得用于恢复，也不能挤掉旧备份。
4. 第一条迁移语句前持久化`prepared`记录；写入/刷盘失败即停止。使用临时文件、刷盘与
   安全替换，不先删除旧记录制造无保护窗口。不承诺所有硬件上的绝对断电安全。
5. 执行现有迁移与校验、孤立访问清理，DB边界全部成功后才结束记录并暴露global DB。
6. 捕获异常时，先持久化`restoring`意图，关闭自有句柄，再尝试恢复。close/日志/记录的
   次级错误不能替换原始异常。句柄未确认关闭时不强行替换当前DB文件。
7. 恢复成功仍保留失败记录阻止原失败流程盲目重试；恢复失败或未完成记录即使pending为空
   也阻止启动。兼容旧marker，不能把有`restoreError`的记录视为过期。

记录存续期间固定其恢复点。正常完成后保持默认三份已验证备份轮换；清理失败不丢弃刚
验证的恢复点。未解决尝试的唯一恢复依据不得被后续备份淘汰。

## 5. 中断与恢复文件顺序

恢复前验证备份、创建同目录临时恢复副本、持久化恢复意图。将已关闭的当前main/WAL/SHM
保留为同一恢复集合，不先删除sidecars；再安装候选并只读验证。验证前不销毁恢复点或原集合。
多文件rename不是单步原子事务：每步失败都要留下可判断状态，重启不盲删残片或猜测回滚。

重启遇到`prepared/restoring/restore-failed`默认拒绝正常业务启动，不自动覆盖可能已升级
成功的数据。现有启动错误路径附本地可操作说明，明确保留文件位置；不新增通用恢复UI。
受控恢复在应用完全关闭后操作，并先保存当前DB/关联用户文件；支持人员按文档在副本上
验证恢复点，成功后才替换。真实恢复需用户另行确认，不为测试读取真实profile。

这不承诺新版成功使用数日后无损降级。旧快照不含后续新增笔记/记录；优先向前修复，确需
恢复时保留当前状态及恢复点差异。不能通过删除marker或台账行来假装修复。

### 验证后解除阻断（独立复核补充）

安全拒启必须有合法结束路径，不能永久锁死或要求手删marker。提供主进程限定的维护入口：
`AlgoLearningPlatform.exe --resolve-upgrade=<attemptId> --resolution=keep-current|retry-source`。
只接受当前profile中已校验记录的ID，不接收任意DB/备份路径，不设生产环境重定向变量。
须持有单实例锁，在主题配置回写、普通服务或窗口启动前执行；第二实例明确拒绝，不传给
普通业务IPC。入口只做检查和记录转换，不自动降级/恢复旧快照，完成后退出并要求正常重启。
应用只在本地故障提示中提供命令与恢复点范围；不新增独立恢复页面。

- `keep-current`：当前库必须精确匹配记录目标台账、对应物理schema及FK/integrity；先备份
  当前状态，再执行幂等孤立访问清理并复验，然后持久化`resolved-keep-current`。用于迁移已
  提交但结束记录未落盘的情况，不把已有新数据换成旧快照。
- `retry-source`：仅在经确认的恢复已完成且当前库匹配记录源台账/schema/FK/integrity时，
  持久化`resolved-retry-source`，允许下一次正常启动建立全新验证过的尝试。该命令本身不迁移。
  执行前说明原失败原因须已处理，不自动循环重试；旧失败审计与当前状态副本继续保留。
- 无法匹配源或目标、记录损坏、恢复集合缺失、检查失败、记录更新失败均保持阻断。
  部分迁移状态不能用`keep-current`跳过剩余迁移。旧marker缺少可信尝试身份时不能绕过验证，
  需按明确的遗留恢复步骤验证并生成关联审计记录后才可解除。
- 解除只由已验证的持久化结果驱动；旧失败记录须关联resolution，不能用“删文件即成功”。
  执行过程中再次中断仍可识别，后续运行重复检查，不静默批准。

旧版记录的目标必须按其真实历史解释：2.0.0 仅认识001–029，不能要求它留下 pending030。
遗留关联以已验证源台账加原 marker 的非空 pending 列表形成当时目标，并严格匹配当前
已知历史的连续前缀。目标重建只执行该段；目标小于当前版本时，解除命令不调用新版
业务清理或迁移，下一次正常启动才建立独立的新恢复点并升级。对应回归必须包含真实
schema28源、pending029、schema29目标，不能只用旧版不可能写出的 pending030 形状。

对应回归：提交后强制结束→正常启动阻断→显式keep-current成功→重启且新增数据保留；
受控恢复源库→retry-source→新尝试；错误ID/状态/schema/记录写入失败仍阻断且无数据损失。

## 6. 配置与导出边界

`config.ts`仅在已有文件确需自动归一化回写时保存受保护的原字节；规范文件与坏JSON继续
原样保留，首次无文件不新增备份。保存/验证失败则不写原配置，使用既有内存降级并安全提示。
不保存解密密钥，不记录配置内容，不自动撤销后续用户保存。普通设置保存保持原契约。

JSON导出v2与应用版本分别管理；继续接受v1/v2并拒绝未来版本。不承诺2.0.0可以读v2，
也不暗中把v2改回v1。版本审查须核对既有对外承诺与真实新增功能；如2.0.1不合适，只报告
原因并请求范围/版本决定，不自动major或要求用户豁免安全。修正文案中将SQLite称为完整
profile备份的错误，说明笔记附件、配置等需分别保护。

## 7. 分支与发布工具

先逐项解决master/dev的22个预检冲突，核对稳定版8类修复的行为；不能整文件选一侧。
通过保留祖先关系的master→dev同步PR（merge commit）消除发布基线分叉；普通修复PR仍squash。
在最终源码树重新跑门，Drizzle PR保持draft、不合入。

采用两阶段发行：准备分支固定版本/CHANGELOG，正常提交评审后合入dev；dev→master通过
no-ff发布PR。发布配置保持npm插件读取package版本但`publish: false`，`increment: false`、
`git.commit: false`，不加载会写文件的conventional-changelog；tag落在master合并提交。
builder显式GitHub provider，所有发布构建使用`--publish never`，生成更新元数据但不上传。

预检要求干净工作区（含untracked）、准确版本、已验收master SHA/合并落点、目标tag/Release
不存在，网络错误不视为不存在。核对确切exe/blockmap/latest.yml、版本、大小与SHA512，
记录源码SHA和资产SHA256。先草稿上传并核对，再公开；失败后先检查外部状态，不盲目重试。
没有electron-updater，不将latest.yml称为已实现自动更新。

## 8. 验证矩阵与明确限制

| 类别 | 必须断言 |
| --- | --- |
| 句柄/台账 | pragma/台账失败close且global未赋值，未来/错名/缺口拒绝，正常历史prefix通过 |
| 备份 | ENOSPC/权限/partial/损坏/错库不进入迁移，旧备份保留，新备份重开可读 |
| 强制结束 | 写入前、030事务中、迁移间、提交后未结束记录各点终止；重启识别未完成，不盲目覆盖 |
| 恢复失败 | copy/rename/sidecar/安装/验证各步故障仍有记录与可恢复数据，pending=[]不能绕过 |
| 次级失败 | close、marker、日志、轮换失败不掩盖原错或消灭最后恢复点 |
| 成功路径 | 历史事实/BLOB/图片引用/时间正确，FK/integrity通过，二次启动无重复备份 |
| 配置 | 原字节备份、失败不回写、规范/坏JSON保持、不泄密、不回滚用户后续保存 |
| 向前修复 | 升级后新增数据在重复启动/修复测试保留，服务启动异常不恢复旧快照 |
| 合法解除 | keep-current验证目标后保留现态，retry-source验证源后允许新尝试；任何校验失败仍阻断 |
| 发布 | 无自动bump/commit/upload，缺任一资产/哈希错/版本错/远程检查失败均阻止公开 |
| 安装 | 隔离Windows安装2.0.0→候选、启动/附件/配置/合成密文保留、卸载留数据及重装 |
